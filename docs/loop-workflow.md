# Codex窓口の反復・再開手順

正本は [workflow-rules.md](workflow-rules.md) 第12・14節。本書はその実施手順と受入条件を定める。正本を緩和する権限は持たない。文書作成時点で実行器・自動再開・定期起動は未実装／未検証であり、稼働中とは扱わない。

## 1. 成立の条件

目的は、長期の決定を引き継ぎ、岡井さんの伝言・再説明・重複承認を減らしつつ、仕様と証拠で完了を判断できること。

最小構成はCodex窓口1、編集担当1、必要な別担当レビュー、既存の検証手段、作業・決定記録、対象に対応する承認である。新しいフレームワーク、定期巡回、Orca worker、複数の同時実装を導入前提にしない。

文書の存在、機能の認識、実行成功、結果回収、停止、再開、権限制限は別々に確認する。試験用モックの成功を実環境の合格として扱わない。

## 2. 三つの反復

| 反復 | 起点 | すること | 終点 |
|---|---|---|---|
| 作業 | 承認済みの目的・合格条件 | 調査、最小変更、検証、原因に基づく修正 | 検証済み、BLOCKED、上限、結果不明 |
| 進行 | 検証・レビュー・承認の結果 | 次工程条件の照合、依頼・回収、記録 | 次の許可された工程、または待機 |
| 手順改善 | 完了、停止、再発の記録 | 手戻りや負担を分析し、改善案を候補化 | 根拠と評価方法を付けた改善案 |

初期導入は作業単位で動かす。候補の発見を変更着手の承認とみなさない。手順改善の反復は、承認基準・レビュー省略条件・権限・hook・sandboxを自動変更しない。

## 3. 開始時の入力

[作業記録テンプレート](tasks/TEMPLATE.md) に沿って窓口Codexが準備する。岡井さんへ記入作業を委ねない。

必須入力は、作業ID、目的、仕様・合格条件の版、対象と範囲、承認の出所と許可操作、レビュー区分、検証方法、反復上限、時間／利用量の枠、記録先、終点である。空欄・未確認・矛盾のある入力は推測で埋めない。

実物の作業先・branch・HEAD・stage・未追跡を含む差分を照合し、保全対象と作業対象を分ける。対象を固定できない間は編集しない。並行する読み取り調査でも、結果には対象版を付ける。

## 4. 通常の一巡

1. 最新の正本、作業記録、仕様、承認と実物を照合する。
2. 「未達の合格条件」「根拠」「最小の変更」「次に確認する結果」を決める。
3. 承認範囲内で変更する。合格条件、承認の記録、保護設定を成功させるために書き換えない。
4. 検証対象を固定し、必要なテストを実行する。検証中に別担当が同じ対象を編集しない。
5. 実行コマンド・終了コード・必要な理由・対象版・生出力の参照を残す。結果をPASS／FAIL／ERROR／NOT_RUNに分類する。
6. 正本第12節の非関与条件を満たす担当へ、対象を固定してレビューを依頼する。実装会話を継承しないことと担当本人の根拠を確認し、PASS／NEEDS_FIX／BLOCKED、対象、指摘、未確認を回収する。満たせない場合は自己点検と区別し、必須レビューが未完了の工程を進めない。
7. 合格条件、指摘、承認範囲、反復上限から次の状態を決めて保存する。

再検証は変更・失敗・不足と影響範囲に絞る。同じ対象・環境・条件で有効な証拠は再利用できる。関連する実行環境や依存が変わった場合は再利用の理由を再評価する。

## 5. 状態と遷移条件

| 状態 | 入る根拠 | 次の行動 |
|---|---|---|
| PREPARED | 目的・範囲・合格条件を記録した | 承認・実物・環境を照合 |
| RUNNING | 入力・許可・実物が一致し、編集担当が一意 | 調査・実装・検証 |
| REVIEW_PENDING | 対象を固定し、証拠を準備した | 必要な別担当レビュー |
| VERIFIED | 全必須条件PASS、必須指摘解消、必要なレビューPASS、対象一致 | 提出、または承認された次工程 |
| RELEASE_APPROVAL_PENDING | 公開が目的に含まれ、判断材料はそろうが承認が不足 | 公開判断を依頼 |
| RELEASED | 対象に対応する承認・保護・checksを確認し、反映結果を取得 | 稼働確認 |
| DONE | 今回の終点を実物と証拠で確認し、記録を保存 | 完了報告 |
| BLOCKED | 範囲外・権限不足・必須確認不足・上限・矛盾 | 対象操作を停止、解消案を提示 |
| UNKNOWN | 変更操作の成否や処理終了が不明 | 既存処理・対象を読み取り確認 |

ERROR／NOT_RUNをPASSにしない。レビュー区分Lの別担当レビュー対象外は、理由を明記したN/Aとして扱い、PASSを捏造しない。必須確認のN/A化はできない。FAILEDな操作があっても作業成果まで失敗と一括判定せず、各状態を分ける。

調査・文書案の提出は、その作業の合格条件と記録を満たせば公開工程を通らずDONEにできる。工程のDONEは、別工程の承認や製品フェーズ完了を意味しない。

## 6. 修正・停止の判定

正本の最大2巡は初回実装後の自動修正全体に適用する。引継ぎ元の作業IDと使用済み巡数を記録し、同じ目的・対象・未解決事項を引き継ぐ後続IDには累積値を持ち越す。不明なら0にせず確認する。1巡は「原因に基づく一まとまりの修正とその検証」。通常のツール呼出し回数と混同しない。最初の編集前に巡数を確保・記録し、中断しても回数を戻さない。子担当・別セッションも同じ作業IDの累積値を使う。

再修正は、具体的な検証失敗またはmust-fix、原因・変更案・次の検証があり、同じ仕様・範囲・権限内である場合に限る。同一失敗で新情報のない結果が2回続いたら、残りの巡数があっても止める。「同一」は対象版、失敗項目、理由から判断し、文言の微差だけで別問題と数えない。

個別のretry禁止・起動1回等は一般的な修正枠より優先する。接続失敗、承認不足、利用制限、unknownをコード修正で解消できると推定しない。権限を上げたり別実行経路へ切り替えたりして突破しない。

時間／利用量の上限は開始前に記録する。小さな受入試験では30分を暫定候補とする。独立した計測・対象処理の停止・後始末が実装で確認できなければ、無人運転を開始しない。APIの費用を観測できない環境では「費用上限保証」を表示せず、観測できる時間・呼出し数等の限界を示す。上限変更をAIが自動承認しない。

## 7. 記録・再開・重複防止

作業記録の更新責任者は窓口Codexに一本化する。最新状態と、変更できない過去の事実を区別する。誤記は訂正理由付きで残し、失敗・無効証拠を成功の履歴へ書き換えない。重要な業務決定は「採用内容・理由・却下した案・承認参照・後継決定」を残す。

将来の実行器は、更新中断時に直前の有効記録を失わない保存方式を用い、並行更新を検出する。対象・記録版・作業IDの一致を必須にする。現時点のMarkdownテンプレートだけで、この保証が実装されたとは扱わない。

外部への変更操作は「未実施／実行中／実施済み／結果不明」を記録する。対象PR・commit・request等の安全な識別子を保存し、応答欠落時はUNKNOWNへ移る。push・公開・worker起動等を無条件に再実行しない。重複を避けるため、操作前の記録と実物の照会手段を用意する。

合格条件・必須テストの変更は正本第12節の基準固定と承認に従う。承認時の版と現行版の差を、作業記録の条件変更欄と照合する。原文・履歴が欠けている場合は同一条件のPASSと判定しない。

再開時には、仕様・承認・対象・差分・担当・巡数・残りの実行枠・進行中処理を照合する。IDを変えて上限を回避しない。前の処理の停止が確認できなければ同じ対象を編集しない。

## 8. 最小の実行基盤

採用候補は、既存のCodex実行手段、機械処理可能な結果、既存テスト、Gitの対象照合、既存の保護機構である。利用する版・実行環境・設定の優先順位・結果経路は実物で確認する。

制御側は、対象IDと版、必須項目、終了コード、証拠参照、巡数、承認、保護条件を照合する。実装担当の最終文章に「PASS」とあるだけで次へ進めない。承認・公開権限・保護条件を、修正担当が自由に変更できる通常作業の範囲から分離する。

機械処理可能な出力も内容の真偽を保証しない。意味・仕様・業務上の影響は必要なレビューで確認する。子担当へread-onlyを指示したことと実効の権限が制限されたことを区別する。

この文書の採用は、CLI更新、環境変数変更、Orca設定変更、接続追加、worktree作成、worker起動、定期ジョブ登録を許可しない。導入する機能だけを別の作業記録に具体化する。

## 9. 導入受入試験（現在は全件NOT_RUN）

文書運用と自動実行器の受入を分ける。文書移行の成立後、最初の手動確認付き試行の前に、利用するCodex環境の承認方式・sandbox・設定の優先関係・拒否時の挙動・停止手段を読み取りと承認された安全な確認で記録する。秘密値は保存せず、役割名やClaude hookから保護を推定しない。必要な制御を確認できなければ、影響する機能の試行を止める。

文書運用の予行ではLOOP-05・06・08・10を、保存した模擬記録や隔離コピーを使って手動確認する。破壊的な実操作や本番への通信で失敗を作らない。この4件の確認だけを自動化の合格にしない。小さな実案件でもLOOP-01・02・03・04・09・11・12の該当する通常・停止条件を省略せず確認し、LOOP-07のような未導入機能は理由付き未実施として残す。自動実行器を導入するときは、下表12件についてfixtureと実効の環境に対応した受入結果をそろえる。

まず隔離したfixtureで判定ロジックを試し、その後、承認された実環境・実効権限で最小の実作業を通す。fixture試験と実環境試験の結果は別欄に記録する。以下は実施予定の受入条件であり、合格記録ではない。

| ID | 条件 | 期待結果 |
|---|---|---|
| LOOP-01 | 正常な小変更、公開未承認 | VERIFIEDで提出または公開承認待ち。外部へ出さない |
| LOOP-02 | 合格条件に反する不具合 | FAILを検出し、原因を示して範囲内修正へ戻る |
| LOOP-03 | コマンド不存在・構文エラー・検証異常 | ERROR。正常DENYやPASSにしない |
| LOOP-04 | レビュー中／後に対象が変わる | 古い結果だけで進めず、対象固定と再確認 |
| LOOP-05 | 同じ失敗・新情報なし2回、または修正上限 | BLOCKED、累積回数と成果物を保持 |
| LOOP-06 | 保存／セッションを途中で中断 | 直前の有効記録から照合、承認と回数を維持 |
| LOOP-07 | 完了通知なし、または結果形式不正 | UNKNOWN／BLOCKED。実行済みと推定しない |
| LOOP-08 | 成否不明の変更操作後に再開 | 実物を先に照会。重複実行しない |
| LOOP-09 | 承認なし／他タスクの承認／範囲外 | 対象操作を止め、許可を広げない |
| LOOP-10 | 合格条件や必要テストの不当な削除・緩和 | 変更を検出し、合格にしない |
| LOOP-11 | 二つの担当が同じ対象を編集しようとする | 二重編集を防ぐ。単なる別プロセス存在とは区別 |
| LOOP-12 | 時間・利用枠・権限の上限到達 | 新規操作を止め、対象処理の終了状態と後始末を確認 |

受入記録には対象版、使用環境、手段、実際の出力、期待との差、終了状態を含める。結果が得られない試験はNOT_RUN／BLOCKEDのまま残す。必須の停止・再開試験が未完了なら、自動運転を有効化しない。

## 10. 試行運用と改善

前節の該当段階の事前確認後、小さな実開発を1件ずつ、合計2〜3件で評価する。直近の比較可能な完了案件1〜2件の記録から、岡井さんの対応時間、AI間貼り付け、重複承認、完了までの時間、修正巡数、公開後不具合、引継ぎ漏れを可能な範囲で再構成する。記録から復元できない値は未計測とし、記憶から数値を作らない。試行でも同じ項目を採り、比較対象のない最初の1件で改善率を捏造しない。

最初の案件では、結果不明の処理がない保存済みの区切りでセッションを替え、記録と参照元から目的・固定条件・承認・残作業・累積巡数を復元できるか確認する。最初の3件はレビュー区分の下げ過ぎも見直す。レビューの有効性は指摘の妥当性・重大な見落とし・再発・証拠の質も合わせて評価し、指摘件数や発見者の割合だけを唯一の指標にしない。

負担や不具合が増える工程は縮小・見直しの候補とする。工程数・エージェント数・テスト件数だけを成果指標にしない。単発の事象から恒久ルールを増やし過ぎず、再現性・影響・再発防止効果から判断する。重要な問題は再発を待たず停止・是正する。

## 11. 導入状態の表示

導入状況は対応する作業記録で管理する。最低限、文書作成、独立レビュー、採用、Git反映、機能確認、fixture受入、実環境受入、試行運用を区別する。本書が存在するだけでは、いずれの工程も自動で完了にならない。

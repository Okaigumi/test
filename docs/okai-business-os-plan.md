# 岡井組 社内業務システム

## 今後のロードマップ案

### 岡井組 業務OS構想 Stage S0〜S7

---

# 1. 構想名

## 岡井組 業務OS構想

ただし、正式な定義としては以下のように狭く定義する。

## 正式定義

**日報起点の現場・原価・帳票・経営判断基盤**

このシステムは、岡井組のすべての業務を無制限に取り込むものではない。
あくまで、**日報を起点に発生する現場情報・人員情報・材料情報・機械情報・外注情報・原価情報・帳票情報をつなぎ、管理者確認と経営判断に活用するための社内基盤** とする。

---

# 2. 最終ゴール

## 最終ゴール

岡井組の現場日報・人員・有休・材料・機械・外注・原価・帳票情報を一元管理し、現場入力から管理者確認、原価管理、帳票作成、経営判断までをつなぐ社内業務基盤を構築する。

最終的には、社長・管理者が以下を即確認できる状態を目指す。

* 全現場の状況
* 工事ごとの利益危険度
* 日報未提出
* 入力異常
* 原価異常
* 請求漏れ候補
* 人員投入状況
* 材料費・機械費・外注費の増加傾向
* 月次確認に必要な帳票・PDF

短く言うと、

**現場入力から経営判断までデータが一本の流れでつながる状態**

を目指す。

---

# 3. やらないことリスト

スコープの暴走を防ぐため、現時点では以下をこのシステムの主目的にしない。

## このシステムで当面やらないこと

* 給与計算そのもの
* 会計処理そのもの
* 工程管理専用システム化
* 写真管理専用システム化
* 入札・積算専用システム化
* 外部業者向けポータル化
* すべてのExcel業務の完全置換
* NAS / OneDrive の完全代替
* kintone の全面置換
* AIによる自動確定処理
* AIによる承認・却下・金額確定

## 判断基準

このシステムに入れるかどうかは、以下で判断する。

**日報起点のデータと直接つながるか。**
**管理者確認・原価管理・帳票作成・経営判断に明確に役立つか。**
**現場入力の負担を増やしすぎないか。**

---

# 4. 基本方針

今後の開発は、以下の方針で進める。

## 開発方針

* 小さいPRで安全に進める
* DB変更・RLS変更・RPC変更は慎重に扱う
* Supabase CLI実行や実DB書き込みは、必要性・影響範囲・手順を明確化してから実施する
* 実装変更は、仕様書・進捗記録・テスト証拠を前提に判断する
* `docs/roadmap.md` は現在地と次の一手を管理する
* 詳細構想は `docs/okai-business-os-plan.md` に分離する
* `CLAUDE.md` には恒久的な実装ルールのみを書く
* 画面ごとに主利用者を明確にする
* 現場入力の定着を最優先にする
* AIは提案・要約・警告・下書きに限定し、確定処理はさせない

# 5. Stage構成

既存のセキュリティ改修Phaseと衝突しないよう、今後の構想は `Phase` ではなく `Stage S0〜S7` として管理する。

| Stage | 名称            | 目的                                          |
| ----- | ------------- | ------------------------------------------- |
| S0    | 基盤安定・仕様整理     | 構想・進捗・セキュリティ残課題・運用ルールを整理する                  |
| S1    | 現場入力・基礎データ    | 日報・現場・従業員・材料・機械・有休などを正確に蓄積する                |
| S2    | 管理者業務の省力化     | 管理者・事務員が毎日の確認作業を短時間で終えられるようにする              |
| S3    | 原価管理ダッシュボード完成 | 工事ごとの予算・累計原価・予算残・危険度を判断できるようにする             |
| S4    | 帳票・請求・書類連携    | 日報・原価データを月次資料、請求確認、PDF、印刷帳票へつなげる            |
| S5    | 社長用 経営コックピット  | 全現場の状況、利益危険度、異常、未提出、請求漏れ候補を一覧化する            |
| S6    | AI支援・自動チェック   | 異常検知、月次コメント、危険理由要約、入力ミス候補検出を支援する            |
| S7    | 将来拡張・外部連携     | 写真管理、電子検査、会計、NAS/OneDrive、kintone等との連携を検討する |

# 18. 判断基準

今後、新機能を追加するかどうかは以下で判断する。

## 追加してよい機能

* 現場入力の負担が下がる
* 日報提出率が上がる
* 管理者の確認時間が減る
* 原価・利益の判断精度が上がる
* 月次確認が楽になる
* 書類作成が楽になる
* 属人化が減る
* セキュリティが強くなる
* 将来の経営コックピットに必要なデータ品質が上がる

## 後回しにする機能

* 見た目だけの改善
* 使う頻度が低い集計
* 仕様が固まっていない機能
* DB設計を大きく壊す割に効果が薄い機能
* 現場入力が難しくなる機能
* 日報起点のデータと直接つながらない機能
* 外部ツールの方が明らかに向いている機能

# 19. 最終的な完成イメージ

最終的には、岡井組の社長・管理者がこのシステムを見れば、以下が判断できる状態を目指す。

* 今日、誰がどの現場で動いているか
* 日報が出ていない人は誰か
* どの現場の原価が危ないか
* どの工事が予算を食いすぎているか
* 材料費・機械費・外注費が増えている現場はどこか
* 請求漏れの可能性がある現場はどこか
* 月次確認で何を見ればよいか
* 会議資料として何を印刷すればよいか
* 次に社長・管理者が確認すべき現場はどこか

この状態をもって、
**「現場日報から経営判断までつながる、岡井組専用の業務基盤」**
として一区切りの完成とする。

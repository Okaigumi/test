# 作業ルール・進捗管理ルール（workflow-rules）

作成日：2026-06-13
対象：岡井組 社内業務システム
更新履歴：Git履歴を参照。Codex窓口への移行条件、レビュー、承認、制御された反復を第12・14節で定める。

本書を運用の正本とする。入口は [AGENTS.md](../AGENTS.md)、Claudeのレビュー入口は [CLAUDE.md](../CLAUDE.md)。製品仕様・フェーズの完了実績は運用変更によって変更しない。第11・13節は当時の履歴として保全する。

**移行の判定**：第12節「移行の有効化」の成立証拠がそろうまでは移行中とし、この案で旧レビュー条件や権限を解除しない。成立後もこの条件説明は残す。文書が置かれたこと、作業記録に完了と書かれたことだけでは成立せず、自動実行の有効化も別に判定する。

## 1. 目的

- 岡井組にとって業務上の効果がある変更を、仕様・証拠・安全確認に基づいて届ける。
- 長期間の開発やセッション切替でも、初期の決定と現在地を引き継ぐ。
- 岡井さんのAI間の伝言、同じ説明、同じ承認、技術的な操作を減らす。
- 各工程の完了と未確認を分け、反復の停滞・範囲拡大・誤った成功判定を防ぐ。

## 2. 基本方針

- 同時に編集する担当は原則1人、実装の本流は1件。本流外は候補として記録する。
- Codex窓口が要望整理・実装・検証・記録・必要な別担当レビューの調整を担当する。
- 既存の未コミット変更、local-only commit、他担当の作業を保全する。
- レビュー担当は対象を編集しない。レビュー・検証中の対象を固定する。
- 承認範囲内の技術判断は継続し、範囲外の操作だけを停止して必要事項をまとめて確認する。
- ルール本文・Skill・プロンプトはOSやGitHubの保護の代用ではない。実効の権限を確認する。

## 3. 本流管理

開始時に [roadmap.md](roadmap.md) の現在の本流、対応する作業記録、製品仕様、承認を確認する。旧履歴の「現在地」を最新状態と混同しない。本流の変更や業務上の優先順位変更は岡井さんの判断を記録する。

承認済みの次工程には、条件を満たせば追加の「続けて」を待たず進む。候補の発見だけを着手承認とみなさない。作業記録と実物が不一致なら影響する操作を停止し、不一致の解消方法を示す。

## 4. 報告するタイミング

- 着手時：目的、範囲、完了条件、不足する承認を簡潔に示す。
- 作業中：重要な発見、方針変更、停止、権限不足、結果不明を知らせる。
- 区切り・中断時：状態と次の行動を記録する。承認済みの通常工程ごとに返答待ちにしない。
- 公開判断時・完了時：業務上の変化、確認できた範囲、残る制約、必要な判断を報告する。

工程ごとの生ログ、ハッシュ照合、AI間の依頼文運搬を岡井さんの通常作業にしない。直接連携できない場合は実行したふりをせず、必要な最小操作を1件にまとめる。

## 5. Git運用

開始時に現在branch、HEAD、stage、未追跡を含む差分、競合作業を確認する。remote-tracking refは取得時点を伴う情報として扱う。古い参照を最新のリモート状態と断定しない。

Git変更操作の承認は第12節で管理する。reset・stash・破棄・強制操作で開始条件を作らない。stageする場合は対象ファイルを明示し、`git add .`・`git add -A`を使わない。commit直前にstageが承認対象だけであることを照合する。

## 6. 範囲の境界

承認済みの調査・実装・テスト・局所修正・文書記録は工程ごとに再承認へ分割しない。仕様変更、範囲追加、依存package・DB・認証・公開・保護設定、費用、破棄、Git変更等は、その操作が既存承認に含まれるか確認する。含まれなければ不足分だけをまとめる。

ついでのリファクタリング・UI改善は候補へ戻す。実DB・SQL実行は岡井さんが行い、Codex／Claudeは実行しない。SQL案の作成にも対象範囲の承認が必要である。

## 7. 記録の正本と役割

| 記録先 | 内容 |
|---|---|
| `docs/workflow-rules.md` | 役割、承認、レビュー、停止・公開条件の正本 |
| `docs/roadmap.md` | 現在の本流への入口、優先順位、製品の進捗・履歴 |
| `docs/tasks/<task-id>.md` | 作業目的、承認参照、仕様・対象、状態、検証、判断、次の操作 |
| `docs/loop-workflow.md` | 正本に従う反復・再開手順、導入時の受入試験 |
| `docs/db-migrations.md` | DB変更・SQL適用・事後確認の記録 |
| `docs/rls-security-plan.md` | セキュリティ設計 |

同じ決定を全文複製せず、正本を参照する。承認の要約を新たな承認の根拠にしない。各AIの会話・memoryは補助情報であり、正式な決定は記録と照合する。

運用規則は本書、個別仕様と合格条件は承認された仕様・作業記録、現在の実行状態は実物と証拠を照合して判断する。roadmapは入口、AIの要約・memoryは補助であり、承認の出所となる岡井さんの直接の指示を置き換えない。最新の明示指示が従来方針を変える場合は変更範囲を記録する。根拠同士や実物が食い違い、許可・仕様を一意に判断できない場合は影響する操作を止める。実物の存在は権限や承認の証明にはならない。

このリポジトリの公開範囲を考慮し、秘密値・個人情報・非公開の内部証拠はGit管理外の承認済み永続保管先へ置く。公開用の作業記録には安全な参照と確認結果だけを残す。一時領域だけを長期引継ぎの保管先にしない。

## 8. フェーズ番号

`roadmap.md` の現在のStage／Phaseと `rls-security-plan.md` の設計上のPhaseを区別する。どちらを指すか明記し、既存の履歴番号や製品完了実績を書き換えない。

## 9. 岡井さんへの報告

先頭は「結果・業務上の効果・確認範囲・残る問題・次の行動／必要な判断」の順で簡潔にする。判断不要なら、承認範囲内の次の行動を示して継続する。詳細な識別情報、ログ、18項目の確認記録は証拠側へ置き、必要時に参照できるようにする。

承認確認文の例は [DEVELOPMENT_WORKFLOW.md](DEVELOPMENT_WORKFLOW.md)。未確認・実行エラーを成功として報告しない。

## 10. 区切り・中断・再開

実装、検証、レビュー、Git操作、公開、稼働確認、中断の区切りで作業記録を更新する。作業ID・対象版・承認・試行回数・有効な証拠・結果不明の操作・次の行動を残す。

再開時は記録と実物を照合する。セッション切替で修正回数・使用枠・承認範囲をリセットしない。結果不明の変更操作は先に実際の成否を確認し、重複実行を避ける。記録保存に失敗したら、新しい変更操作を開始しない。

## 12. Codex窓口・レビュー・承認・実行手順

### 移行の有効化

この節への移行変更自身は重要な運用変更として扱う。基準は移行前の正本（commit `30f087b49f33af867bb27d354f0e34d0589fc0e3` の本ファイル）。作成に関与していないClaude担当の独立レビュー、指摘の解消、対象照合、岡井さんの対象限定の採用・Git／merge・公開承認がそろうまで、新ルールでこの移行を自己承認しない。commit／push等の個別の既存承認は対象内で引き継ぐが、未承認の操作を推定しない。

文書移行の成立には、(1)対象版を特定した非関与ClaudeのPASSと指摘解消、(2)対象を示す岡井さんの採用・必要なGit操作の承認原文または確認可能な参照、(3)その対象版がmainへ反映されたcommitと対象文書の一致、の3つを読み取りで照合する。比較元・レビュー対象・反映commitを作業記録または承認済み永続証拠に記録する。mainと同名のローカルbranchや古いremote-tracking refだけで成立を判定しない。証拠が不足する、または対象が違う間は移行中として扱う。

成立を確認した担当が、その証拠参照と確認日時を作業記録へ追記する。記録への追記を自己承認の代わりにはせず、レビュー済みの過去版も残す。この条件文の削除を移行完了のための別作業として要求しない。成立後の新規作業から文書上のCodex窓口運用を開始し、この移行自身の判定には旧ルールを維持する。自動実行・自動再開・定期起動の有効化は別工程とし、[loop-workflow.md](loop-workflow.md) の実環境確認と受入試験に合格した機能だけを、対象限定の承認後に使う。文書採用だけで、自動実行や新しい設定の導入が承認されたとは扱わない。

### 役割

- 岡井さん：業務目的、優先順位、重要な仕様、費用、採用、本番反映を判断・最終承認する。
- Codex窓口：要望整理、代替案、仕様案、調査、実装、テスト、自己点検、記録、必要な別担当レビューの調整、承認されたGit／PR／公開と結果確認を担当する。実リポジトリにアクセスできる担当を作業記録に明示し、他環境の状態を推測しない。
- レビュー担当：対象の設計・実装・修正に関与していない別セッション／別エージェントが、読み取り専用で仕様・実物の差分・証拠を確認する。作者の自己評価を合格根拠にせず、対象を編集しない。新しいセッションというだけで独立性を断定せず、担当と非関与を記録する。
- Claude：重要な変更の追加レビューを担当する。通常の窓口・実装担当・Git／公開担当ではない。自ら設計・編集した対象は、別の非関与担当がレビューする。

非関与レビューとして採用するには、担当本人が次の条件と根拠を記録する。窓口は依頼記録・対象・返却結果と照合し、作者の宣言だけで成立させない。

1. 当該作業IDとその引継ぎ元の、対象の設計判断・実装・修正に参加していない。レビュー指摘や最小修正案の提示だけは編集への参加とみなさないが、実装を代筆・共同設計した担当は除く。
2. 実装者の会話・推論履歴を自動継承しない別のコンテキストで開始する。セッションの名前変更や会話を継承した子エージェントだけでは満たさない。作成方式・履歴継承の有無・非関与を確認できなければ自己点検として扱う。
3. 正本、承認された仕様・合格条件、対象識別、実物の差分と関連するソース、検証の生証拠を渡す。作者の結論への同意を指示しない。担当が必要な実物・仕様を独自に読み、対象一致と反例・不足を確認する。修正再確認では過去の指摘も渡す。
4. 担当・セッションまたは実行ID・独立したコンテキストの根拠・参照した資料・対象版・結果を、レビュー担当自身の報告として残す。仕様と証拠の共有は必要であり、共有資料があるだけで非関与を否定しない。

親が起動した担当でも上記を実証できればN区分の別担当レビューに使用できる。ただし同一モデルの見落としの相関は残り、異種モデルの確認と同等とは主張しない。Hおよびこの移行自身には非関与Claudeを必要とする。

Codexの自己点検、窓口の状態報告、`/okg-status`の所見は別担当レビューの代替ではない。Codex別担当による確認を「Claude独立レビューPASS」と表示しない。同一モデルに共通する見落としの可能性を踏まえ、重要な変更は追加レビューを必須とする。

### 影響によるレビュー区分

| 区分 | 条件 | 必須確認 |
|---|---|---|
| L：軽微 | 動作・業務意味・権限・運用規則に影響しない誤字等だけ。理由と差分で示せること | 差分と必要な表示確認。必須の別担当レビューは対象外とする理由を記録 |
| N：通常 | 承認された通常の画面・動作変更で、Hに当たらない | 必要なテスト、自己点検、非関与の別担当レビュー。Codex別担当を使用可能 |
| H：重要 | 認証・権限・金額計算・DB／データ削除・実バックアップ・公開設定・依存package・hook／保護・運用ルール、または影響判定不能 | 影響・復旧方法の確認、必要な検証、非関与Claudeの追加レビュー。専門判断が必要なら対象を示して相談 |

HのClaudeレビューは、通常レビューの必要観点も覆えば兼ねてよい。同じ対象の形式的な重複レビューを増やさない。行数・拡張子だけで区分を下げない。個別仕様が要求するHuman Review・検証・停止条件は、区分Lでも省略しない。変更中にHの要素が判明したら、その操作を止めて区分・承認・確認範囲を更新する。

### 標準工程

岡井さんの依頼 → 正本・仕様・実物・承認の照合 → 作業記録と合格条件の具体化 → 不足する判断をまとめて確認 → 実装・検証・自己点検 → 区分に応じた別担当レビュー → 範囲内の修正・再確認 → 対象照合 → 承認されたcommit／push／PR・Preview → checksと公開判断の準備 → 対象限定の公開承認 → merge・公開・稼働確認 → 記録。

調査や文書案だけの依頼では、その成果物を終点とする。必要な工程を実施できなければ未確認とし、外部へ出す操作を止める。レビュー不要のLも、理由、検証、対象照合、公開の承認が必要である。

### レビュー対象と証拠

- コミット済み：BASE、対象HEAD、対象ファイル、差分を記録する。PRでは実際のbase／headから求めたmerge-base以降の全変更を確認する。
- 未コミット：基点HEAD、未追跡を含む対象一覧、完全な内容識別情報と差分を記録する。追跡済みは `git diff --full-index`、未追跡は `git diff --no-index --full-index -- /dev/null <対象ファイル>` 等、許可された方法で実物と照合する。no-indexの差分を示す終了コード1と実行エラーを区別する。
- 検証・レビュー中の対象を固定し、実施前後の一致を確認する。不一致の証拠は無効として分離する。対象変更後は変更と影響範囲を再確認する。
- レビュー結果は `PASS / NEEDS_FIX / BLOCKED`。指摘には箇所・根拠・影響・must-fixの有無・解消案・未確認事項を付ける。実施できない確認は `BLOCKED` とし、推測でPASSにしない。
- テストは `PASS / FAIL / ERROR / NOT_RUN` を区別する。拒否を期待する場合は期待終了コードと必要な理由を確認し、任意の非0を正常拒否とみなさない。実装同一ロジックの期待値計算だけで正しさを証明しない。
- 承認時の合格条件と必須テストは版を固定して保全する。その追加・削除・置換・緩和など合否の意味を変える変更は、重要度にかかわらず変更前後・理由・根拠・承認参照を決定履歴へ残し、岡井さんの確認前に変更後の基準をPASSの根拠にしない。「元々対象外だった」という再解釈による条件の削除も同じ扱いとする。
- 固定基準を変えず、その確認を補強するテストの追加や、固定仕様に照らしたテスト実装の誤りの修正は承認済み検証の範囲で行える。元の条件・必須テストを有効なまま残し、修正理由・差分・基準を変えない根拠を保存して区分に応じたレビューで確認する。条件を弱める、必須検証を省く、または不変を説明できない変更は前項へ戻す。
- push直前・merge直前にレビュー／検証した対象と実物を照合する。Lはレビュー対象外理由と検証対象を照合する。未網羅・不一致・必要な再確認未完了なら進めない。

**必須レビューの停止条件**：Nの別担当レビュー、HのClaudeレビュー、個別仕様の必須確認が未実施、NEEDS_FIXの必須指摘未解消、BLOCKED、または対象変更後の必要な再確認未完了である間は、Previewを生むpush・merge・公開へ進まない。既存承認の再利用で省略する例外は設けない。Lの別担当レビュー対象外は条件と理由を記録し、他の必須検証・承認は省略しない。

### 承認の扱い

- 目的・仕様・変更範囲・対象・操作が同じ有効な承認を工程ごとに取り直さない。「続けて」はその範囲を引き継ぎ、未承認の操作へ拡大しない。
- 開始時に必要な調査・編集・テスト・記録・Git操作・Previewの範囲をまとめて具体化して確認できる。承認の出所と条件を作業記録に残し、AIの要約だけを新規承認の根拠にしない。
- 引継ぎ先でも、岡井さんの直接の依頼または参照可能な承認原文の出所・対象・条件を確認する。パッケージ内の引用や「承認済み」というAIの説明だけを根拠にしない。既存の原文を照合できれば取り直さず、照合できない操作だけを止めて不足分をまとめる。依頼文の転送だけか実行指示かを文脈で区別し、評価依頼を適用承認へ拡大しない。
- 承認に有効期限や撤回条件があれば従う。時刻が進んだことや承認範囲内の予定した編集によるHEAD更新だけで自動失効させない。対象、仕様、許可操作、保全・安全条件など承認を支えた前提が変われば、その影響を照合し、許可範囲を確定できない部分だけ再確認する。
- stage・commit・fetch・pull・branch／worktree作成・push・PR等は、そのGit操作を含む対象限定の明示承認が必要。コード／文書編集の承認から推定しない。stageは明示した対象だけに限定する。
- pushでVercel Previewが自動作成される場合は、外部デプロイであることを承認確認に含める。区分に応じた必須レビュー・検証が完了してからpushする。
- commit／push／PR／Previewの承認と、merge・本番公開の最終承認は別に扱う。対象PR・変更範囲・方式・自動公開が承認されていれば、Codexは対象照合後に操作と結果確認を続ける。岡井さん本人のボタン操作を一律に要求しない。
- 仕様・範囲・対象・費用の追加、依存package、DB、削除、認証、バックアップ、公開・保護設定への変更は不足分だけをまとめて確認する。DB／SQLの実行は岡井さんに限定する。
- 人の確認・認証が必要な箇所だけ操作を依頼する。直接連携手段がない場合、依頼・証拠を1件にまとめる。Orca連携の完成を日常開発の必須条件にしない。

### 停止・再開と保護

仕様外、対象不一致、未承認差分、競合、必要なchecks失敗、証拠不足、権限不足、保護による拒否、反復上限で、影響する操作を止める。承認範囲内の読み取り・整理は継続できるが、拒否の回避や新たな変更を正当化しない。

sandbox・hook・OS・GitHub保護は承認とは別に適用する。管理者実行、ACL／所有者変更、保護無効化、別経路への切替による回避、force push、強制mergeを行わない。Claude用hookがCodexも保護すると推定しない。役割名やプロンプトだけでread-onlyや実行上限を保証しない。

実装の初回後の自動修正は、原因・変更・次の検証を説明できる局所的な範囲内修正に限り最大2巡とする。検証の具体的失敗またはreviewerのmust-fixを根拠にし、重要度だけで自動判断しない。任意の改善は候補に戻す。同一失敗で新しい情報がない結果が2回続いたら停止する。個別の「1回のみ・retry禁止」があれば優先する。セッション／子担当をまたいで回数を合算し、再開でリセットしない。

時間・利用量の枠を作業開始前に定める。小さな導入試験では30分を初期候補とし、実効の計測・停止手段を確認する。実行器が上限を保証できない状態では無人運転を有効にしない。時間切れを成功やプロセス終了と同一視せず、対象処理の状態を照合する。

### 機密資産・補助機能

[機密資産の利用規則](private-assets-local-usage.md) に従う。秘密値・本番データを報告・差分・通常ログへ出さず、機密保管先を一般の作業対象へ追加しない。

`/okg-go`はType 1限定のClaude read-onlyレビュー、`/okg-status`はread-only状態所見を返す任意の補助手段として維持する。日常の状態取得はアクセス可能なCodexが担当し、Claudeコマンドの実行と岡井さんによる結果の転送を必須工程にしない。Claudeでの確認が必要な個別依頼に限って使い、直接返却できなければ窓口が証拠の受渡しを1件にまとめる。編集・Git変更の権限は与えない。今回の運用文書変更でhookの許可コマンドを拡張しない。

Skill・Superpowers・subagentは補助手段であり、本書の権限や停止条件を変更しない。機能の存在、認識、実行成功、結果回収、停止・再開、権限の確認を区別する。新規接続・設定・自動実行の導入は、対象・権限上限・停止・復元方法を具体化し、Hのレビューと明示承認後に使う。

## 14. オーナー目的とType 1 frontend-only運用ルール（恒久）

### オーナー目的

目的は「岡井組にとって総合的にプラスになる社内業務システムを作ること」。画面要望は手段として扱い、業務効率、社員・管理者・経営者の負担、安全性、信頼性、保守性、費用対効果、過剰実装、代替案を評価する。

より良い案は理由とともに示す。重要な仕様変更は確認し、承認範囲内の技術判断は継続する。初期の決定、採用しなかった案、その理由は作業記録へ残す。会話・memoryは正式な根拠を置き換えない。

### Type 1の境界

Type 1と `/okg-go` はfrontend-only（表示、文言、CSS、レイアウト、スマホ対応、ボタン、モーダル、カレンダー等）に限定する。DB／SQL／RPC／RLS／認証／session／PIN／allow-guard／settings／migration／データ削除等が必要なら対象操作を停止する。金額計算や権限へ影響するものを表示変更として扱わない。

新規Type 1実装は、main・clean・競合なし・open PR 0・ahead／divergeなし、合意BASEと確認したリモートmainの一致、予定branch名の未使用を確認する。既存差分のレビューはcleanを要求しない。文書移行等の非Type 1は、個別に承認した基点と保全条件を用いる。未コミット変更を自動で片付けない。fetch／pull／branch作成も第12節の承認に従う。

### 品質工程と報告

preflight → 仕様・価値・区分確認 → 承認されたbranch／実装 → 必要なテスト → frontend-design・security・test-evidenceの3観点の自己点検 → 第12節の区分に応じた別担当レビュー → 必要な修正・再確認 → 対象照合 → 承認されたGit／Preview／PR → checks → 公開判断の準備、と進む。

自己点検のために3人のエージェントを毎回起動する必要はない。レビュー結果と自己点検結果を混同しない。反復上限・停止・再開は第12節に集約し、別の回数枠を作らない。critical／high未解消、必須指摘の未解消、重大なレビュー矛盾があれば公開へ進まない。N・Hを含む必須レビュー未実施／NEEDS_FIX未解消／BLOCKED時のPreviewを生むpush・merge・公開の停止は、第12節「必須レビューの停止条件」を適用し、既存承認で省略しない。

従来の18項目（結論／岡井組への効果／推奨と理由／仕様の項目別照合／変更内容／変更していない範囲／既存機能への影響／frontend-design・security・test-evidence各review／static・自動テスト／Vercel checks／残存リスク／未確認事項／Preview確認項目／復旧方法／branch・commit・PR・base・head整合性／決めてほしいこと）は、作業・検証記録で確認可能にする。別担当レビューの担当・対象・結果、またはLの対象外理由も残す。毎回18項目を岡井さんの画面へ全文転載せず、第9節の簡潔な報告と詳細参照を使う。

仕様照合は「実装済み／未実装／変更あり／対象外／確認不能」で分類する。合格条件が未実装・変更あり・確認不能なら、検証済み・完了へ進めない。

### mergeの判断・承認と実行

merge・本番公開の判断者は岡井さん、承認された操作の実行担当はCodex。対象PR・変更範囲・方式・付随する自動公開への明示承認を確認し、直前に全差分のレビュー・検証の網羅、対象HEAD、checks、保護条件を照合する。Claudeはmerge操作・コマンド提示をしない。

条件を満たす場合だけ承認されたmerge・公開を実行し、mainへの反映、対象SHA、デプロイ結果、必要な稼働確認を記録する。Previewの確認を本番の確認済みとして流用しない。結果不明なら再実行前に状態を取得する。

「実装済み」「検証済み」「公開承認待ち」「公開済み」「稼働確認済み」を分ける。調査・文書案の提出が終点の作業では、公開を前提にしない。AIの処理終了、通知の受信、CIの一部成功だけで作業全体を完了にしない。

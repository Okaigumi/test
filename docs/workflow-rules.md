# 作業ルール・進捗管理ルール（workflow-rules）

作成日：2026-06-13
対象：社内業務システムプロジェクト全体

状態：恒久ルール（特定フェーズ専用ではなく、プロジェクトが続く限り継続適用する）

本書を運用の正本とする。入口は [AGENTS.md](../AGENTS.md)、Claudeの担当範囲は [CLAUDE.md](../CLAUDE.md) を参照。製品仕様・フェーズの完了実績は、本書の運用ルールの変更によって変更しない。merge・公開の前提となる独立レビューの完了とレビュー対象の照合は、第12・14節に定める。役割と承認済み作業の進め方は第12節、Type 1とmergeの境界は第14節に集約する。

## 1. このファイルの目的

- 社内業務システムプロジェクト全体の作業ルールを定義する
- 進捗管理チャットへ報告すべきタイミングと報告内容を定義する
- 実装チャットと進捗管理チャットを混ぜないためのルールを定義する
- 作業中に本流から逸れないようにする

---

## 2. 基本方針

- 原則、同時に進める実装は1つだけにする
- 本流以外は保留扱いにする
- 進捗管理チャットでは、作業指示よりも判断・整理を優先する
- 読み取り専用確認と変更作業を混ぜない
- 作業範囲を超えそうになったら、作業を止めて報告する
- 未コミット変更やブランチのズレがある場合は、作業前に状態確認を優先する

---

## 3. 本流管理ルール

- 作業開始時に、現在の本流を確認する
- 本流とは、現時点で最優先で進める1つの作業テーマを指す
- 本流以外の作業が出た場合は、原則として保留扱いにする
- 本流を変更する場合は、進捗管理チャットで判断してから行う

---

## 4. 進捗管理チャットへ報告すべきタイミング

以下のタイミングでは、Codexは進捗管理チャットへ貼れる報告を出す。承認済み範囲内の報告は再承認待ちを意味せず、第12節に従って続行する。

- 作業単位が一区切りついたとき
- 次フェーズに進めそうだと判断したとき
- SQL作成に進みたくなったとき
- SQL実行に進みたくなったとき
- コード修正が必要に見えたとき
- docs更新が必要に見えたとき
- git add / commit / push が必要に見えたとき
- reset / stash / ファイル削除 / 破棄操作が必要に見えたとき
- 本流以外の作業が混ざりそうになったとき
- 未コミット変更を検出したとき
- ローカルブランチが origin/main と大きくズレているとき
- デバッグに入るべきか迷ったとき

---

## 5. git運用ルール

- 作業開始時に現在ブランチ、git status、git log --oneline -5 を確認する
- main が origin/main とズレている場合は、勝手に作業を進めない
- ahead / behind がある場合は、作業前に報告する
- local-only commit がある場合は、勝手に消さない
- reset / stash / checkout / branch作成 / rebase / merge / pull / push は、明示指示がある場合のみ行う
- origin/main を基点に作業する必要がある場合は、専用ブランチを作る方針を提案する
- 作業ツリーが clean でない場合は、まず状態確認を優先する

---

## 6. 禁止事項

次の操作は承認範囲外では行わない。承認済みタスクに含まれる調査・仕様案・コード／文書の修正・検証・自己修正・記録を工程ごとに再承認へ分割しない。Git変更・DB実行等の区別は第12節に従う。

- SQL作成
- SQL実行
- コード修正
- docs更新
- git add
- commit
- push
- reset
- stash
- rebase
- merge
- ファイル削除
- 破棄操作
- 本流以外の実装作業
- ついでのリファクタリング
- ついでのUI改善

## 9. 進捗管理チャット用の報告フォーマット

進捗管理チャットへ貼る報告は、以下のフォーマットを使用する。

```md
## 作業報告

### 現在の本流
-

### 現在の作業
-

### 実施内容
-

### 確認できたこと
-

### 未確認・不明点
-

### 発見したリスク
-

### 現在の作業範囲内か
範囲内 / 範囲外の可能性あり

### 本流以外に混ざりそうな作業
-

### 未コミット変更の有無
-

### ブランチ状態
-

### 次に進んでよいかの判断材料
-

### CLIとしての提案
- 継続
- 停止して判断待ち
- 別チャットへ分離
- 次フェーズ移行の相談
```

## 10. 作業の区切りごとの報告義務（進捗管理チャット貼り付け用）

作業が以下のような「区切り」に到達した場合、CLIは次に進む前に、進捗管理チャットへそのまま貼れる形式で、**現在地・完了内容・確認結果・次にやること**を必ず整理して報告する。

この報告は Section 4（報告すべきタイミング）を具体化したものであり、区切りごとの報告を毎回省略しないことを徹底するための恒久ルールとする。

### 区切りの例

- DB実行完了
- DB事後確認完了
- 本番確認完了
- docs記録完了
- commit完了
- push完了
- PR作成完了
- PR merge完了
- main追従完了
- ブランチ整理完了
- フェーズ完了
- 次工程へ移る直前
- 作業を中断する直前

### 報告文に原則として含める項目

- 現在地（どのフェーズ・どの区切りにいるか）
- 完了した作業
- 確認結果（DB事後確認・本番確認・git status など、確認できた事実）
- 未実施のこと（今回あえてやっていないこと）
- 次にやること
- 注意点や別タスク候補（本流外として切り出したもの・申し送り事項）

### 補足

- 区切りに到達したら、次の変更作業へ進む前に、まずこの報告を出す。
- 報告の詳細フォーマットが必要な場合は Section 9 のフォーマットを併用してよい。
- 報告は「進捗管理チャットへそのまま貼れる」ことを前提とし、実装チャットの作業ログと混ぜない（Section 1・Section 2 参照）。

## 11. allow-guard 許可範囲の拡張（2026-07-21・PR #158 記録）

## 12. Claude窓口・Codex実行の役割、承認、実行手順

### 役割

- 岡井さんはClaude窓口へ要望を伝え、業務要件と優先順位を踏まえて、仕様・変更範囲・採用・公開を判断し、最終承認する。本人による目視・認証が必要な確認は、その必要箇所に限定する。
- Claudeは岡井さんの唯一の窓口として、要望整理、Codexへの作業依頼、結果の取りまとめ、進捗管理、独立レビュー、岡井さんへの報告・承認依頼を担当する。Codexの変更と検証証拠について、仕様との整合、scope外変更、証拠の有効性、未確認事項の扱いを確認する。窓口であることは、通常の実装担当、Git／公開操作の実行担当、最終決定者になることを意味しない。
- Codexは実装・修正の主担当として、承認範囲内の調査、仕様案、実装、テスト、自己点検、証拠作成、指摘修正、記録と、承認されたGit／PR／公開操作を実行する。変更箇所・影響範囲・対象識別情報・判断根拠・未確認事項をClaude窓口へ返す。Codexの自己点検やCodex側のsubagentレビューを、Claudeの独立レビュー完了に読み替えない。
- 「必要箇所に限定する」「レビュー対象を絞る」とは、Claudeが確認する変更箇所・影響範囲・証拠を具体化する意味であり、Codexの判断だけで標準工程の独立レビュー自体を省略する意味ではない。Claudeの独立レビューを実施できない場合は「独立レビュー未実施」と明記し、実施済みとして扱わない。個別仕様のHuman Review・検証・停止条件は維持する。
- Claudeが自ら作成・修正した部分は、同じClaudeセッションの自己点検で独立レビュー済みにしない。修正に関与していない別のClaudeセッションまたは編集を行わないClaudeレビューエージェントが確認する。Claudeの窓口業務、進捗報告、`/okg-status`の状態所見も独立レビューの完了にはならない。
- 岡井さんにエージェント間の伝言や依頼文の貼り付けを原則として求めない。ClaudeからCodexへ依頼できる既存手段がない場合に限り、Claudeが依頼を1回分にまとめ、岡井さんに必要な最小操作を一度に示す。直接連携を実行したふりをしない。この運用を理由に、ClaudeやCodexの判断だけで接続や設定を新規導入しない。
- ClaudeとCodexの直接連携のために接続・hook・設定を導入する場合は、対象、許可する操作、権限の上限、停止条件、元に戻す方法を具体化し、岡井さんの明示承認を得る。変更はCodexが承認範囲内で行い、Claudeの独立レビュー（Claudeが設計・作成した部分は、修正に関与していない別のClaudeセッションまたは編集を行わないClaudeレビューエージェントによる確認）を完了してから使用する。承認は導入した範囲に限り、権限の拡大、保護の無効化・迂回、他の接続や設定への包括許可の根拠にしない。
- 第1〜10節に残る「進捗管理チャット」「実装チャット」「CLI」は、現在の報告経路では原則として「CodexがClaude窓口へ報告し、Claudeが岡井さんへ必要事項を整理して伝える」と読み替える。第11・13節は当時の履歴として書き換えない。

### 標準工程

岡井さんからClaude窓口への依頼
→ Claudeが要望を整理してCodexへ作業依頼
→ Codexが調査・変更内容を具体化してClaude窓口へ返却
→ Claudeが必要な仕様判断・承認を岡井さんへ依頼
→ Codexの実装・テスト・自己点検・証拠作成
→ Claudeの独立レビュー（確認した対象を記録）
→ 指摘があればCodexが修正・再検証し、Claudeが再確認
→ commit・push・PR作成の承認がある場合、Codexがレビュー済み内容を照合して操作を実行
→ Codexがmerge判断報告を作成し、Claude窓口が岡井さんへ提示
→ Claude窓口を通じた岡井さんによるmerge・付随する公開の最終承認
→ Codexがレビュー済み内容とPR対象HEADの対応を照合し、承認されたmerge・公開結果確認を実行

Claudeの独立レビューは、ローカルcommit前の差分またはローカルcommit後・push前の差分を対象にする。どちらの場合も下記「レビュー対象の記録と照合」に従い、レビュー済み内容との一致を確認してからpushする。レビュー後に内容を変える場合は、変更と影響範囲についてClaudeの再確認を完了してからpushする。commit・push・PR作成の承認と、merge・付随する本番公開の最終承認は別の承認として扱い、前者からmerge・本番公開の承認を推定しない。既に得ている明示承認は、その対象・範囲・操作の中で引き継ぐ。

Vercelの自動Previewは本番公開ではないが、外部へのデプロイである。未レビューの内容をPreviewへ出さない。pushによってPreviewが自動作成される場合、pushの承認確認文にその事実を明記する。

調査だけの依頼や、個別仕様に別の停止条件がある場合は、その承認範囲と停止条件に従う。標準工程は、未承認の変更・Git操作・公開操作を許可する根拠にはしない。

### レビュー対象の記録と照合

- CodexはClaudeへのレビュー依頼に、確認対象を再現できる識別情報を作成して提示する。Claudeは許可された読み取り操作で実物と照合し、レビュー結果に確認した対象を記録する。Claude自身に別のハッシュ取得コマンドの実行を一律必須としない。
  - コミット済みの対象：BASE（比較元commit）、HEAD（対象commit）、対象差分（`BASE..HEAD` の変更ファイル一覧）。
  - 未コミットの対象：基点HEAD、未追跡を含む対象ファイル一覧、追跡済みファイルは `git diff --full-index`、未追跡ファイルは `git diff --no-index --full-index -- /dev/null <対象ファイル>` のindex行に示される完全なblob識別情報と対象差分。`git diff --no-index`は差分があると終了コード1になるため、出力内容とエラーを区別する。
- Claudeは許可された `git diff --full-index` と、未追跡には `git diff --no-index --full-index` を使用して、Codexが示したindex行・対象差分と実物を突き合わせる。短縮ハッシュや行数だけで内容一致と判断しない。改行コード変換等でblob識別情報を比較できない場合は、完全な内容差分で一致を確認し、その方法と限界を記録する。
- push前とmerge前に、Codexはレビュー済み内容との対応を照合する。PR差分は実際のPRのbaseとheadから求めたmerge-baseを比較元とし、`merge-base..HEAD` の全変更が、いずれかのレビュー記録（複数可）で覆われていることを確認する。ローカルの`main`や`origin/main`は取得時点を記録し、古い可能性がある追跡参照だけでリモート未反映と判断しない。
- レビュー後に内容が変わった場合、照合で差異が見つかった場合、レビュー済み内容とpush対象を照合できない場合、またはPR作成後にレビュー対象とPR対象HEADを照合できない場合は、その変更と影響範囲をClaudeが再確認し、対象を記録し直す。必要な照合ができない間は、Previewを生むpush・merge・公開へ進まず状況をClaude窓口へ報告する。承認範囲内の調査・指摘修正・検証は継続する。

### 承認の扱い

- 合意済みの目的・範囲・制約内では、技術判断、必要な修正、検証、記録を継続する。同じ承認を岡井さんへ繰り返し求めない。「続けて」は直前の合意範囲を引き継ぎ、未承認の操作へ拡大しない。岡井さんへの承認確認文の書き方と例は [開発運用の補足](DEVELOPMENT_WORKFLOW.md) を参照し、承認の判断基準は本書に従う。
- 対象PR、変更範囲、merge方式、付随する自動公開まで明示承認されていれば、CodexはDraft解除、承認された方式でのmerge、デプロイ結果確認まで一貫して実行できる。同じ対象・範囲・操作への有効な明示承認は工程ごとに再要求せず、岡井さん本人によるmergeボタン操作も一律には要求しない。承認の再利用は、Claudeの独立レビューや必要な検証を省略する理由にはしない。
- Claudeの独立レビューが未実施、レビューで必要とされた修正・再確認が未完了、レビュー済み内容とpush対象を照合できない、またはPR作成後にレビュー対象とPR対象HEADを照合できない場合、Previewを生むpush・merge・公開へ進まない。既存のpush・merge・公開承認を再利用して、この条件を省略しない。未実施のまま進む例外は設けない。この停止は外部へ内容を出す操作に対するものであり、承認範囲内の調査・指摘修正・検証・記録は継続する。
- 承認は対象限定であり、将来の別PR、追加変更、DB操作、設定変更への包括許可ではない。Claudeの編集・Git操作権限はこの実行委任では広げない。Claudeは変更箇所・影響範囲に絞った独立レビューを担当し、対象を絞ることはレビュー自体の省略を意味しない。
- 承認済みの同じ作業で、目的・変更範囲・対象ファイル・実装内容・リポジトリの変更範囲がすべて変わらず、作業前確認の不備や停止原因の解消だけを行う場合は、その解消作業が既存承認に含まれることを確認したうえで、同じ承認を引き継ぐ。承認・検証の条件を緩めたり、sandbox・hook・OSの保護を変更・迂回したりする根拠にはしない。
- 範囲追加、対象ファイルの追加、製品仕様／承認基準の変更、package・DB・migration変更の必要、既存承認を超えるリポジトリ変更、未承認のcommit・push・merge・公開、取り返しのつかない操作、実DB・実バックアップ・公開・認証やOrca設定の変更は、その操作まで既存承認に含まれるか確認する。含まれない場合、追加する対象・変更内容・理由・影響・推奨案を具体化し、不足分をまとめて一度に確認する。
- stage・commit・push・PR作成・branch変更等は、当該Git操作を含む明示承認が必要。コード／文書編集の承認だけで実行しない。mergeは第14節に従う。DB変更・SQL実行は岡井さんが行い、Codex／Claudeは実行しない。
- sandbox・hook・OSのアクセス制御は承認とは別に適用される。拒否時は操作と理由を記録し、正規のワークスペース選択や許可手続きを使う。管理者実行、ACL／所有者変更、保護無効化、別手段による迂回はしない。
- 未承認差分、対象PR・branch・HEAD等の不一致、checks失敗、同じ対象での競合作業、権限不足、保護ルールによる停止があれば、対象操作を止めて状況を報告する。差分の取込み、force push、保護回避、管理者による強制mergeで解消しない。別プロセスの存在だけでは競合作業と判定しない。

前記の承認引継ぎは、この停止条件やレビュー対象の照合条件を解除するものではない。

### 作業の進め方

1. 本書、現在の本流・仕様、承認範囲を確認し、HEAD・差分・他の実行中作業を確認する。既存の未コミット変更を保全し、同時実装は第2節の1件を守る。
2. Codexが影響、既存の呼出元、代替案を調べ、変更内容を具体化して、仕様との照合と実施方針を示す。必要な仕様判断・承認を得た後は、範囲内の工程切替で同じ承認を取り直さない。
3. Codexが承認範囲だけを実装し、変更に適したテストと自己点検を行い、差分、仕様、秘密情報の混入、既存機能への影響、文書参照を確認して証拠を作成する。既存の有効な証拠で確認できる項目は再実行せず、変更・失敗・不足がある項目に絞る。
4. Claudeが変更箇所・影響範囲・仕様・検証証拠を独立レビューし、確認した対象を「レビュー対象の記録と照合」の形式で記録する。指摘があればCodexが承認範囲内で採否を検証して修正・再検証し、Claudeが再確認する。実施できない場合は「独立レビュー未実施」として未確認事項に残し、Previewを生むpush・merge・公開へ進まない。
5. Codexが第7節の記録先へ結果・証拠・未確認事項・レビュー対象を残してClaude窓口へ返す。commit・push・PR作成は、その操作を含む明示承認がある場合だけ実行する。commit前にレビューを受けた場合はローカルcommit後の内容、commit後にレビューを受けた場合はレビュー対象commitを照合し、レビュー済み内容だけをpushする。pushでVercel Previewが自動作成されることを承認確認文に含める。第9・10節と第14節に沿ってCodexがmerge判断報告を作成し、Claude窓口が岡井さんへ提示する。実行結果と証拠で確認できた範囲を区別し、Previewの証拠を本番確認済みとして流用しない。非公開の実環境情報・内部証拠本文はGit管理外へ保全する。
6. 岡井さんがmerge・付随する公開を最終承認した後（既存の有効な明示承認は範囲内で引き継ぐ）、Codexは独立レビューと必要な修正・再確認の完了、レビュー済み内容とPR対象HEADの対応、保護条件、checksを直前確認し、承認されたmerge・公開操作だけを実行して対象SHAとデプロイ結果を記録する。いずれかを満たさない場合はmerge・公開へ進まない。未承認のGit操作、DB、公開等へ進まない。

### 機密資産と既存コマンド

- 機密資産の入力・出力・一時保存と利用例は [機密資産の外部保管](private-assets-local-usage.md) を参照する。Orcaの通常作業フォルダや一般読取り対象に機密保管先を追加しない。秘密本文・パスワード・接続トークンをログ、差分、報告へ出さない。

## 14. オーナー目的とType 1 frontend-only運用ルール（恒久）

### オーナー目的と要望の扱い（恒久・全作業に適用）
- オーナーの目的は「**岡井組にとって総合的にプラスになる社内業務システムを作ること**」。
- 画面要望は目的ではなく、その**手段・入口**である。字義どおりに追認しない。
- Codexは各要望について、**業務効率・社員/管理者/経営者の負担・安全性・信頼性・保守性・費用対効果・過剰実装・代替案**を評価し、Claudeの独立レビューは第12節に従う。
- より良い案があれば**理由とともに提示**する。承認済み範囲内の判断はCodexが進め、範囲や仕様の重要変更は第12節に従う。
- Claude の私的 memory 領域は補助情報に過ぎず、**正式な根拠はリポジトリ内文書（本ファイル等）**とする。

### CodexのType 1実装とClaudeのレビュー入口
- この工程と `/okg-go` のレビューは **Type 1 frontend-only 専用**（対象例: 表示・文言・CSS・レイアウト・スマホ対応・ボタン・モーダル・カレンダー等）。DB/SQL/RPC/RLS/認証/session/PIN/allow-guard/settings/migration/データ削除等は対象外で、判明したら変更せず停止する。
- 承認済み仕様を入力とし、**preflight → branch → 調査 → Type1/価値確認 → 実装・テスト → 3レビュー（frontend-design・security・test-evidence 必須のCodex自己点検）→ 必要なら承認済みのローカルcommit → Claudeの独立レビュー → レビュー済み内容との照合 → push・Vercel Preview・PR作成 → checks → merge判断報告** を品質上の工程とする。Claudeのレビューはローカルcommit前後の差分を対象にし、レビュー済み内容だけをpushする。push後に内容を変える場合は、変更と影響範囲の再レビューを完了してから次のpushを行う。Codexの自己点検やsubagentレビューだけでClaudeレビュー済みとしない。commit・push・PR作成はその操作の承認がある場合だけ実行し、pushの承認確認にはVercel Previewが自動作成されることを含める。Previewは本番公開ではないが外部へのデプロイとして扱う。merge・付随する本番公開の承認がなければmerge判断報告で停止し、承認済みなら下記条件に従ってCodexが続行する。`/okg-go`自体は実装・Git操作を行わず、Claudeの独立レビュー結果をClaude窓口の取りまとめへ返す。
